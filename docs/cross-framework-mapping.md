# Cross-framework mapping

## Cross-Framework Mapping

This matrix maps every technique to four external references:

| Framework | What It Provides |
|-----------|-----------------|
| [HackMyAgent](https://github.com/opena2a-org/hackmyagent) | Automated detection (318 static checks, 164 attack payloads) |
| [DVAA](https://github.com/opena2a-org/damn-vulnerable-ai-agent) | Lab validation (21 agents: 16 deliberately vulnerable, 1 hardened reference, 4 control-protected variants; 12 vulnerability categories) |
| [OASB](https://oasb.ai) | Defensive controls (46 controls across 10 domains) |
| MITRE ATT&CK / ATLAS / OWASP LLM | An index of which techniques this repository's mapping documents name against each framework, and which they do not |

See [cross-references/](../cross-references/) for detailed mapping documents. The DVAA figures are pinned in [`related-projects.json`](../related-projects.json) with the DVAA release they were read from. On each line naming DVAA in README.md and in the pages that took its reference text (`PAGES` in the script, this page among them), `python3 scripts/check_readme_claims.py` reads the wordings "N agents", "N deliberately vulnerable", "N hardened reference", "N control-protected variant(s)", "N vulnerable agent(s)" and "N categories" (up to two words, each a run of ASCII letters and hyphens, may stand between the number and "categories"), in any letter case with one space between words, and fails when one states a different number. A DVAA figure worded any other way is not checked. A line naming DVAA fails the check when it carries a format character (Unicode category Cf, such as a soft hyphen or a zero width space), a control character other than a tab, a Hangul filler, a combining mark that Unicode lists as default ignorable, such as a variation selector, or a code point that Unicode lists as default ignorable without assigning it, because such a character can keep a figure from being read while the line still shows it. A line names DVAA when it contains "DVAA" once such characters are removed, either as it then stands or after three more steps, with no combining mark (Unicode category M) directly after it that NFKC joins to the last A. So "DVAA" followed by U+0301 COMBINING ACUTE ACCENT, which NFKC joins to the A as U+00C1 LATIN CAPITAL LETTER A WITH ACUTE, does not name DVAA, nor does "DVAA" followed by U+0332 COMBINING LOW LINE and U+0301, while "DVAA" followed by U+0332, U+0335 COMBINING SHORT STROKE OVERLAY, U+0338 COMBINING LONG SOLIDUS OVERLAY or U+20DD COMBINING ENCLOSING CIRCLE, which NFKC leaves apart from the A, names DVAA. A mark counts as directly after "DVAA" only where it is written as itself, not as a character reference, directly after a letter or another mark, and a mark that does not is kept apart from the name, so that NFKC in the third step below does not join it to the last A: `DV**AA**` followed by U+0301, `DVAA&#x301;`, `DV**AA**&#x301;` and `DV**AA&#x301;**` name DVAA, while NFKC alone gives "DVA" followed by U+00C1. Where white space other than a space or tab follows a tag name, the line is also read with only a space, a tab or `/` ending a tag name. Where a character other than an ASCII letter, digit, hyphen, tab, line feed, form feed, space, `/` or `>` follows a tag name, such as `\`, `<` or U+00A0, or where a tab, line feed, form feed, space or `/` follows a tag name and a `<` follows that before any `>`, the line is also read as a browser reads a tag in an HTML block, with a name that is an ASCII letter followed by any characters other than a tab, line feed, form feed, space, `/` and `>`, the six characters at which a browser ends a tag name, so that U+00A0 and U+3000 IDEOGRAPHIC SPACE do not end one, and after the name and a tab, line feed, form feed, space or `/` a tag runs to the first `>` after it, past any `<`, which a browser reads there as part of an attribute name or value: `DV<x\>AA`, `D<D\\</b>VAA`, `DV<x` followed by U+00A0 and `<y>AA`, `DV<a <b>AA`, and `D<a <b` followed by U+00A0 and `D<x\>VAA` name DVAA. Where `/` or white space follows a tag name and a `"` or `'` follows that before any `<` or `>`, the line is also read with each quote in a tag after that `/` or white space passed over whole with the text up to the next such quote on the line, as an attribute value in quotes, which CommonMark and a browser read past any `<` or `>` it holds: a tag then runs to the first `>` that stands in no such value if no `<` that stands in none comes first, so `DV<b x="<">AA` and `DV<b title='>'>AA` name DVAA. A quote that no such quote follows on the line is read there as any other character. Where `&` stands directly before `#`, the line is also read as a browser reads an HTML block: its tags are read as a browser reads them, as above, and each numeric character reference (`&#` followed by one or more ASCII digits, or by `x` or `X` and one or more hexadecimal digits, with a `;` directly after the last digit where one stands) is decoded in the first step where it stands as written, with or without the `;` and whatever its number of digits, and what it stands for, less any such character, is kept as text. As a browser reads a reference before it reads any tag, its digits end at the first character after them that is not such a digit in the line as written, such as `<` or `*`, so `&#x30<b>D<x\>VAA` reads "0DVAA" and names DVAA, as do `DVA&#65`, `DVA&#x41` and `DVA&#00000065;`, where CommonMark reads a reference only with the `;` and at most seven decimal or six hexadecimal digits and shows each of the three as written in a paragraph. No such reference starts inside HTML or a code span, or at an escaped `&`. Where a `"` or `'` stands on a line read either of these two ways as a browser reads an HTML block, it is also read that way with each quote in a tag after the tab, line feed, form feed, space or `/` that ends its name passed over whole with the text up to the next such quote on the line, as above, and the tag then running past any `<` to the first `>` that stands in no such value, as a browser reads a tag name, a quoted value, a `<` in a tag and a reference at once there. A line read with quoted values passed over is also read the first of those two ways with them passed over, as a `<` that stands in no such value can follow one: `DV<b x=">" <c>AA`, a tag `b` holding the value `>` with an attribute `<c`, names DVAA, as do `DV<x\ y=">">AA`, a tag named `x\` holding the value `>`, `DV<a <b x=">">AA` and `DV<b x='>'>A&#65`. Each of these readings is also made with the text of each `style`, `script` and `template` element removed, as a browser shows none of it: going along the line, a start tag removed as above whose name is `style`, `script` or `template` opens that element unless a `style` or `script` element is open, and an end tag removed as above closes the element opened last where it has that element's name, each name read in any ASCII letter case and, whichever reading removed the tag, as the HTML block reading reads a tag name, to the first tab, line feed, form feed, space, `/` or `>`; where a start tag opens an element while none is open, what stands from that start tag to the end of the end tag that closes the element, or to the end of the line where none does, is removed. So `DV<style>x</style>AA`, `DV<script>x</script>AA`, `DV<template>x</template>AA` and `DV<template><template></template>x</template>AA` name DVAA, while `DV<style>x</script>AA`, `DV<style` followed by U+00A0 and `>x</style>AA`, and `DV<style>x</style` followed by U+00A0 and `>AA` do not. The line names DVAA when any reading does. On the way, as CommonMark reads them, the character a backslash escapes (an ASCII punctuation character directly after it) and the text of a code span are kept as text, which no later step reads as markup, HTML, a link span or a character reference; the backslash and the backticks around the code span are removed, and a backslash before any other character stays. A run of backticks opens a code span that the next run of as many backticks on the line closes, and the text between them loses one space at each end when it starts and ends with a space and holds another character. No code span is read on a line that carries one of the characters above, nor on the lines after a line where, read with no link label removed as below, code spans are not read or stop being read or a run of backticks finds no closing run, up to a blank line. Going along the line, where a `]` that no backslash escapes and that stands in no code span or HTML is directly followed by a link label (the `[` and the text after it to the first `]` that no backslash escapes, with no `[` that no backslash escapes before that `]`, as CommonMark bounds a label though of any length), the `]` is removed with the label when the label is blank (empty or of white space only) or one that the page holding the line defines, and no HTML, escape or code span starts inside the label; otherwise the `]` stays, and the `[` and what follows it are read on. A page defines a label where, once such characters are removed, it holds a `[` that no backslash escapes followed by that label, a `]` and a colon, two labels being the same when they are after Unicode case folding, with white space at either end removed and each run of white space inside read as one space. A page holding a definition-like text that CommonMark does not read as a definition, such as one in a fenced code block, defines the label here too. Where a `]` is so directly followed by a `[`, the line is also read with no label removed and, where two or three labels the page defines stand directly after a `]` on it, with each other mix of them removed and kept, and it names DVAA when any of its readings does. A line holding four or more such labels is read with all of them removed and with none and, where one to three of them are labels the page defines on no definition line, with each other mix of those removed and kept and the others removed. A definition-like text stands on a definition line where its `[` starts a line, after at most three spaces, outside a fenced code block: so `[t]: x` does as a line of its own, also after one to three spaces, while `` `[t]: x` ``, `[t]: x` after four spaces or a tab, and `[t]: x` on a line in a fenced code block do not. A fenced code block runs from a line that, after at most three spaces, starts with a run of three or more backticks with no backtick after it on the line, or of three or more tildes, to the first later line that is, after at most three spaces, a run of that character at least as long followed by nothing but spaces and tabs, or to the end of the page. So `[x][DV](url)AA`, which CommonMark shows as "[x]DVAA" where the page does not define the label `DV`, names DVAA, as does `[x][DV](u)[A][t]A` on a page that defines `t`, with `DV` only in a fenced code block, which CommonMark shows as "[x]DVAA", and `[x][DV](u)[A][t]A [y][a] [z][b]` on such a page that also defines `a` and `b`, which CommonMark shows as "[x]DVAA y z", while `[DV][dvaa]AA` names DVAA only where the page defines the label `dvaa`. Second, going along what remains, each `]` followed by `(` is removed with the text after it to the first `)` if no further `(` comes first, whether or not they make a link, then each `!` directly before a `[`, and then the Markdown characters `*`, `_`, `~`, `` ` ``, `[` and `]`. Each reading is also made with no such `]` removed with the text after it, as CommonMark shows the `]` and the `(` as text where no `[` before them opens a link that the `]` closes: so `x](DV**AA**)` and `x](DV<style>x</style>AA)`, each shown as "x](DVAA)", name DVAA, and so does `[x](DV**AA**)`, whose link destination CommonMark does not show, as `[x](DVAA)` does as it stands. Third, its character references are decoded, each to the characters it stands for less any such character, so `&#8203;` (U+200B) leaves nothing, and it is brought to Unicode NFKC with each character that Unicode lists as confusable with A, D or V, such as U+0410 CYRILLIC CAPITAL LETTER A, read as that letter. On a line that carries one of the characters above, a combining mark after "DVAA" does not keep the line from naming DVAA, so "DVAA" followed by U+200B and U+0301 names DVAA and the line fails on U+200B. A line of README.md or those pages that states one of the `matrix.json` counts once such characters are removed fails the same way, and each failure gives the line and column of the character.

The HackMyAgent and OASB figures are pinned in [`related-projects.json`](../related-projects.json) too, with the HackMyAgent release they were read from. The check reads "N static checks", "N payloads" and "N attack payloads" against the pinned HackMyAgent figures and "N controls" and "N domains" against the pinned OASB figures, on every line of README.md and those pages in that letter case, and fails when one states a different number. The title of each OASB-1 control is pinned there from the same release, under `oasb.controlTitles`: the Mitigation section of each technique page lists the controls `matrix.json` maps to the technique with their titles, and `python3 scripts/check_technique_pages.py` fails when a section differs from that rendering or when `matrix.json` maps a control with no pinned title.
