# Schema

`matrix.json` follows `schema/threat-matrix-v1.2.schema.json` (JSON Schema 2020-12). `scripts/validate_matrix.py` checks the file against that schema and the rules the schema cannot state (ids resolve, `replacedBy` and `parentId` present exactly when required, `technique-ids.json` in sync, a `wildSampleCount` above 0 wherever `wildPrevalence` is above 0). `matrixCommit` in `technique-ids.json` is the 40-character sha of the commit whose `matrix.json` the id list indexes; the validator refuses a value of any other shape, and in a checkout that has the commit's history it also refuses a sha that names no commit or whose `matrix.json` carries different ids (a shallow checkout without that commit, a partial clone without that commit's tree or `matrix.json`, or a copy without git, gets the shape check only, and the validator's summary line says which check ran). Technique ids may take the form `T-NNNN.NNN` for a sub-technique, listed flat in `techniques` with a `parentId`; `schema/consumer-readiness.json` keeps dotted ids out of the file until the listed consumers accept them. `stix/agent-threat-matrix-bundle.json` is a STIX 2.1 rendering of the matrix produced by `scripts/generate_stix.py`, with deterministic object ids; the validator fails when the committed bundle differs from a fresh rendering. Every STIX object takes its `modified` date from `updated` in `matrix.json`, so when the file's content other than `updated` differs from the committed copy the validator also requires `updated` to be no earlier than the current date. Evidence tiers are defined in `docs/evidence-tiers.md`, which the Evidence Standard table on that page, `CONTRIBUTING.md` and `EVIDENCE_AUDIT.md` quote; `scripts/check_evidence_tiers.py` reads those three pages and `README.md` and checks that each definition written there on a line of the form `| **Observed** | <definition> |` or `- **OBSERVED**: <definition>` quotes it word for word, that such a list-item definition ends on its line (the next line is a bulleted list item with text indented no further than it, or is blank and the first line after the blank lines is indented less than the text of the definition's list item, which starts after the spaces and tabs that follow the marker, or one column after the marker when those cover five or more columns), and that each of the three pages defines every tier. It reads a list item and a code block where CommonMark reads one: a line whose marker is followed by a no-break space, or is indented four or more columns past the text of the list item it is inside (past the margin when it is inside none), is not a definition and does not end one, and a code fence ends with the list item it is in.

Every technique carries `wildPrevalence`, a number from 0 to 100, and `wildSampleCount`, a whole number from 0, and the file carries `wildPrevalenceSource`, the endpoint they were read from and the read date; the schema requires all three. The registry computes both from its honeypot telemetry. `wildPrevalence` is callbacks per page visit in the technique's category, as a percentage rounded to two decimals and capped at 100, and 0 where the category has no page visits; the callbacks are the canary fires in the technique's category and the payload callbacks of the payloads mapped to the technique. `wildSampleCount` is those callbacks plus those page visits. They measure engagement with a honeypot, not a production attack rate. `python3 scripts/sync_wild_prevalence.py` reads the registry endpoint `https://api.oa2a.org/api/v1/threat-matrix` once, writes on each technique the two values the endpoint serves for it, or 0 for both where it serves none, records the endpoint and the read date, and gives each technique it writes a `wildSampleCount` above 0 for one `honeypot-telemetry` evidence entry citing that endpoint and read date, and the other techniques none; when that changes the file, it moves `updated` to today if it is older and renders the STIX bundle and `evidence-gaps.json` again. It writes nothing when the response does not parse or lists none of the technique ids, or when it holds a prevalence outside 0 to 100, a sample count that is not a whole number of 0 or more or is too large for a 64-bit float, or a prevalence above 0 with a sample count of 0. `--payload` with `--read-date` reads a saved response instead of fetching one. The two values do not set or change a technique's evidence tier.

A technique's optional `evidence` array lists the sources it rests on, each with a `type`, a `reference` and a `date` (see [Evidence entries](evidence-tiers.md#evidence-entries)). The validator refuses an entry whose reference does not resolve to a source it reads, and an entry that repeats the type, reference and date of another entry on the same technique. A `honeypot-telemetry` entry resolves when its reference is the `wildPrevalenceSource` url, its date is the read date there, and the technique's `wildSampleCount` is above 0. A `lab-reproduction` entry resolves when its reference is the permalink of a DVAA scenario page that `evidence-sources.json` pins, `<repository>/blob/<commit>/<path>`, its date is the date of the commit in that permalink, and the page names the technique's id with the technique's name as the label. It also resolves when its reference is the permalink of a DVAA challenge, `<repository>/blob/<commit>/src/challenges/index.js#L<line>`, or of a scenario page that `evidence-sources.json` pins for a technique's `dvaaValidation`, its date is the date of the commit in that permalink, and a value of the technique's `dvaaValidation` (the text between its commas, trimmed) is the challenge's id or the scenario's name. `evidence-sources.json` follows `schema/evidence-sources.schema.json`, which the validator also checks, and `python3 scripts/pin_evidence_sources.py --dvaa <clone>` writes it, with those entries, from a git clone of DVAA. No other reference resolves: the validator reads no other source, so a citation it cannot read is refused rather than taken on trust. `python3 scripts/generate_stix.py` carries each entry into the `external_references` of its technique's attack pattern, and writes and prints `evidence-gaps.json`, the sorted ids of the techniques with no evidence entry; the validator fails when that file differs from a fresh rendering, so a gap closes when an entry that resolves is added, and the list is never edited by hand. The References section of the technique's page lists each entry in one `- Evidence:` line directly under the Tactic link, with the entry's type, date, reference and note; `python3 scripts/check_technique_pages.py` fails when those lines differ from `matrix.json`, and its `--fix` writes them.

The top-level `dataSources` is the data source vocabulary: telemetry a defender can collect to see a technique. An entry is admitted only with `readBy`, one or more citations of a tool or sensor that reads the data, each giving the tool's name, the GitHub `repository`, the 40-character `commit` sha, and the `path` and `line` of the reading code at that commit. A technique's `dataSources` lists objects, each naming a `source` from the vocabulary, the `tool` that uses it, whether that use is a `check`, a `signature` or a `sensorField` (its `kind`), and `ref`, the check id, signature id or sensor field name as the tool writes it. A technique with no such use is left unmapped. The validator refuses an entry without a citation, an empty `readBy`, and a mapping whose `tool` the source's `readBy` does not cite; it checks the shape of a citation, not the cited file. It also refuses a mapping whose `tool` is `hackmyagent` and whose `kind` is `check` when its `ref` is not one of the technique's `hmaChecks`. [Data sources](data-sources.md) lists the vocabulary, with a link to the line each entry cites, and the techniques that map no data source; `scripts/check_technique_pages.py` renders that page from `matrix.json`.
